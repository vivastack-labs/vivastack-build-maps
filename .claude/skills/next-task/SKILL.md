# next-task：次のタスクに着手してPRを作る

このリポジトリは、開発計画のタスクを **1タスク＝1ブランチ＝1PR** で進める（`docs/development-plan.md` 1.2）。
このスキルは、その手順を毎回同じように行うためのもの。各手順の「なぜ」を書いてあるので、
想定外の状況では理由に照らして判断する。

ユーザーへの確認は、`AGENTS.md` のとおり**推奨案と理由を付けて**聞く（Claude Code では AskUserQuestion を使う）。
スクリプトはこのファイルと同じディレクトリの `scripts/` にある（以下 `<skill>/scripts/`）。

## 1. main に切り替えて最新にする

```bash
git status --porcelain
git config --get-all remote.origin.fetch | grep -qxF '^refs/heads/screenshots' \
  || git config --add remote.origin.fetch '^refs/heads/screenshots'
git update-ref -d refs/remotes/origin/screenshots
git switch main && git pull --ff-only
```

- 2〜3行目：`screenshots` ブランチ（PRの画像）を、この後の `git pull` と手順2の `git fetch --prune` で取らないようにする。取ると、PRが増えるたびに画像のダウンロードが増える。設定してあれば何もしない。4行目は、前に取った追跡ブランチを消す（`--prune` では消えない）。なければ何もしない。

- 作業ツリーに変更があれば、**切り替える前に止めて**ユーザーに確認する。変更を失わないため。
  推奨は「今のブランチにコミットする」（理由：stash は忘れられやすい）。
- `--ff-only` が失敗したら（main にローカルだけのコミットがある）、止めて状況を伝える。main には直接 push しない決まりなので、何かがおかしい。

## 2. ローカルブランチを片付ける

```bash
bash <skill>/scripts/branches.sh
```

main 以外のブランチを、紐づくPRの状態で分類して出す（`git fetch --prune` も行う）。

| action | 状況 | すること |
|---|---|---|
| `delete` | PRがマージ済み・クローズ済みで、PRの後のコミットがない | 確認せずに `git branch -D <branch>` |
| `ask` | PRがない | 削除するか保留するかを確認する |
| `ask` | PRがオープン中 | 同上。レビュー対応中の作業があることが多い |
| `ask` | マージ済み・クローズ済みだが、PRの後にローカルだけのコミットがある | 同上。消すと戻せない |

- `-D` を使うのは、squash マージだと `-d` が「マージされていない」と判断して失敗するため。PRの状態で確かめてあるので安全。
- `ask` のブランチは、まとめて1回で確認する。推奨の目安：
  - `local_only` が 0（コミットがすべてリモートにある）→ 削除を推奨（リモートから戻せる）
  - `local_only` が 1 以上 → 保留を推奨（消すと戻せない）
  - オープン中のPR → 保留を推奨
- 「削除」と答えたブランチだけを `git branch -D` で消す。消したブランチと残したブランチを一覧で報告する。

## 3. タスクを選ぶ

```bash
python3 -I <skill>/scripts/task_status.py
```

計画の表（状態）・`docs/tasks/*.md`（依存関係）・GitHub のPRを突き合わせて、実際の状態を出す。
PRは、ブランチ名に `/<ID>-` を含むか、タイトルに `<ID>` を含むものをそのタスクのPRとみなす
（だから手順4・8の命名規則を守る）。

- **タスクIDを指定された**：依存がすべて完了しているか確かめる。終わっていない依存があれば、どれが残っているかを伝えて確認する。
- **指定されていない**：「着手できる」から選ぶ。
  - 1つだけならそれに着手する。
  - 複数あれば確認する。推奨は表の上にあるもの（理由：計画の順番は、後のタスクの依存が早く解ける順になっている）。並行できるタスクは計画の第4章を見る。
- 「作業中」のタスクがあれば、選ぶ前に伝える。別のセッションで進めているかもしれない。
- 「着手できる手作業」（例：T0-05）は、オーナーの作業なのでPRは作らない。残っていることを報告にだけ書く。
- 「依存関係の補足」があれば読み、部分的な制約（例：「ブランチ保護だけは T0-04 の後」）を計画に反映する。
- T5-05（残りの46県）は県ごとにPRをくり返すので、マージ済みのPRがあっても「完了」とは限らない。表の状態を正とする。

## 4. ブランチを作り、計画の状態を更新する

ブランチ名は `<種別>/<タスクID>-<英語の短い説明>`（例：`chore/T0-02-component-e2e-tools`）。

```bash
git switch -c <種別>/<タスクID>-<slug>
```

`docs/development-plan.md` 第3章の表を直す：

- スクリプトの「計画を「完了」に直す」にあるタスク → `完了`。main に直接 push できないので、状態だけを直すPRを別に作らず、ここでまとめて直す。
- これから着手するタスク → `作業中`。

この変更を最初のコミットにする：`docs: <完了にしたID> を完了、<着手するID> を作業中にする`。

## 5. 読んで、実装計画を作り、承認を取る

読むもの（全部読んでから計画する。後から読むと手戻りになる）：

1. `docs/tasks/` のタスクの定義（目的・参照仕様・実装内容・完了条件・テスト条件・依存関係）
2. 参照仕様に挙がった `docs/development-overview.md` の章・要件ID・決定事項（D）・未決事項（U）
3. `docs/development-plan.md` 第4章（未決事項）で、「決めるタスク」がこのタスクの行。推奨案と理由が書いてある
4. Next.js のコードを書くなら、`node_modules/next/dist/docs/` の該当する章（`AGENTS.md`）

実装計画を `.claude/PRPs/plans/<タスクID>-<slug>.plan.md` に書く（`<slug>` はブランチ名と同じ。Claude Code では `/prp-plan` で作れる）。
計画ファイルは**コミットして残す**。なぜその方針にしたかを、後のタスクやレビューで読み返せるようにするため。少なくとも次を入れる：

- 先に書くテスト：テスト条件を1つずつ、テストのファイルとテスト名（要件IDを入れる）に落としたもの
- 作る・変えるファイルと、その順番
- 完了条件を1つずつ、どう確かめるか
- **判断が必要な点**：未決事項、仕様と実際が違いそうな点、版の選び方など。それぞれ推奨案と理由を付ける

ここで**止まって承認を取る**。計画の要点と、判断が必要な点を**すべて**示す（要点だけに絞ると、示さなかった判断まで承認されたことになってしまう）。
コードを書く前にオーナーが方向を確かめられるようにするため（`docs/development-plan.md` 1.3）。
修正を求められたら計画を直し、もう一度確認する。

承認されたら、計画ファイルをコミットする：`docs: <タスクID> の実装計画を追加`。

## 6. TDD で実装する

承認された計画のとおりに進める（`.claude/rules/testing.md`）。

1. テスト条件のテストを書き、**失敗することを確かめる**（Red）。失敗を見ないと、テストが本当に振る舞いを確かめているかが分からない。
2. 通る最小の実装を書く（Green）。
3. 整える（Refactor）。イミュータブル、小さな関数、境界での入力検証（`.claude/rules/coding-style.md`）。

- 1ファイルのテストは `pnpm vitest run <path>`、全体とカバレッジは `pnpm test`。
- Claude Code の Bash では、pnpm の前に `source ~/.nvm/nvm.sh && nvm use` が必要（`CLAUDE.md`）。
- 仕様・タスクの定義と実際（ライブラリの挙動、データの中身など）が違ったら、`docs/development-plan.md` 1.3 に従う。
  オーナーの判断が必要なものは確認し、採用した内容で仕様とタスクの定義を**同じPRで**更新する。
- 後のタスクに関係する発見（例：T0-01 で分かった `out/` の構成）は、該当するタスクの定義に書き足し、PRの「分かったこと」にも書く。
- 承認された計画から変える必要が出たら（ライブラリの制約、端末名の違いなど）、オーナーの判断が要るものは確認する。変えた内容と理由は、手順8の前に計画ファイルへ書く。
- コミットは区切りのよいところで、`<type>: <日本語の説明>` の形式で。

### Claude Code では、実装を Sonnet のサブエージェントに任せる

計画・判断・最終確認はメインのセッション（Opus）が行い、テストと実装を書く作業は `task-implementer` エージェント（Sonnet）に任せる。
理由は2つある。Sonnet は Opus の半分の単価で、計画どおりに TDD を進める作業には十分なこと。
それと、計画のために読んだ設計書がメインの文脈に残ったまま実装すると、コマンドを1回実行するたびにその大きな文脈を読み直すことになり、費用の多くがそこにかかるため（T1-06・T1-07 のセッションで確かめた）。
Codex では、上の手順を自分で行う。

1. Agent ツールで `task-implementer` を呼ぶ。依頼文には次を書く：
   - 計画ファイルのパス、タスクID、ブランチ名、スクラッチパッドのパス
   - 承認のときにオーナーが決めたこと・付けた条件（計画ファイルに書いていないもの）
   - E2E やスクリーンショットを頼むかどうか（ふつうは頼まない。手順7でメインが行う）
2. 報告の `status` で分ける：
   - `done` → 手順7へ。
   - `blocked` → 「判断が要ること」を、推奨案と理由を付けてオーナーに確認する。答えを SendMessage で同じエージェントに返し、続けさせる（文脈が残っているので、新しく呼ぶより安い）。
   - `failed` → 失敗の内容を読み、直し方を SendMessage で示す。2回返しても直らなければ、メインで調べる。
3. 報告の「計画から変えたこと」「分かったこと」は、手順8の計画ファイルとPRの本文に使う。

- サブエージェントの報告をそのまま信じない。手順7で、メインがコマンドを実行して確かめる。
- Agent ツールでは、`task-implementer` を名前で指定する。モデルはエージェントの定義（`model: sonnet`）で決まる。

## 7. 完了条件を確かめ、レビューする

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm build
pnpm test:e2e   # 導入済み（T0-02 以降）なら
```

- タスクの定義の完了条件を1つずつ確かめる。コマンドで確かめられないもの（例：「カバレッジが基準を下回ると失敗する」）は、実際に試して結果を記録する。
- 共通の完了条件（`docs/development-plan.md` 1.1）：上のコマンドが通る、カバレッジが基準以上、レビューで CRITICAL・HIGH の指摘がない。
- コードレビュー（Claude Code では code-reviewer エージェント）を行い、CRITICAL・HIGH を直す。MEDIUM もできるだけ直す。
- 失敗したまま先に進まない。hooks や検査を回避しない（`--no-verify` は使わない）。

### Claude Code でのレビューと修正の分け方

- **レビューは Opus で行う。** Agent ツールで `code-reviewer` を呼ぶときに `model: "opus"` を指定する（定義の既定は Sonnet で、ほかの使い方のために変えない）。
  レビューは出力が少なく、判断の質が結果を左右するので、ここに Opus を使っても費用は小さい。
  依頼文には、計画ファイルのパス、比べる範囲（`git diff main...HEAD`）、タスクの完了条件を書く。
- **指摘の修正は、手順6の `task-implementer` に SendMessage で返す。** 指摘を CRITICAL・HIGH・MEDIUM に分けて渡す。
  報告が戻ったら、直した内容を確かめる。CRITICAL・HIGH を直したときは、もう一度レビューする。
- **最終確認はメインで行う。** 上のコマンドをメインで実行する（出力が長いので、`2>&1 | tail -n 40` のように末尾だけを見る）。
  完了条件を1つずつ確かめるのもメインが行う。サブエージェントの報告は、どこを見るかの手がかりに使う。

### 画面が変わるタスクでは、before/after のスクリーンショットを撮る

オーナーがPRの上で、画面の変わり方を確かめられるようにするため。

1. そのタスクで変わった状態（例：県を選んでパネルを開いた状態）を、`tests/screenshots/pages.spec.ts` の `SCENES` に足す。各言語のトップは最初から入っている。クライアントで描く要素（地図の SVG など）は、`prepare` で表示されるのを待ってから撮る。
2. コミットしてから撮る（after は今の作業ツリーで撮る）。

```bash
pnpm screenshots > <スクラッチパッド>/screenshots.md
```

- before は `origin/main` を worktree に取り出して撮り、after は今の作業ツリーで撮る。どちらも、撮る画面は今のブランチの `tests/screenshots/` を使う。main にまだない画面は before が「なし」になる。
- `pnpm install` とビルドを before・after で2回ずつ行うので、数分かかる。Playwright の chromium が要る。
- 画像は、`<ブランチ名の / を - にしたもの>/before・after/` だけを入れた commit として、`screenshots` ブランチの先頭に push される（main とは履歴を共有しない。消さない）。PR本文の URL は commit を指すので、後のPRや撮り直しで過去のPRの画像は変わらない。push の前に取るのは先頭の commit だけで、過去の画像はダウンロードしない。
- 出力された Markdown（「画面の変更」の節）を、PR本文に入れる。撮り直したら、PR本文の表も貼り替える（URL が commit ごとに変わる）。
- 画面が変わらないタスクでは撮らず、PR本文に「画面の変更なし」と書く。

## 8. 計画ファイルを実際の内容に合わせ、PRを作る

PRを出す前に、計画ファイルを実際に作ったものに合わせて直す。古い計画が残ると、後で読んだ人やエージェントが、実際とは違う内容を正しいと思ってしまうため。

- 先に書くテスト・作る・変えるファイル・判断が必要な点を、実際のテスト名・ファイル・採用した内容に直す。
- 承認のときから変えた点は、末尾に「承認後に変えたこと」の表（項目・承認したとき・実際・理由）で残す。なければ「なし」と書く。
- `pnpm lint`（markdownlint）が通ることを確かめ、コミットする：`docs: <タスクID> の実装計画を実際の内容に合わせる`。
- PRの「判断したこと」と、計画ファイルの内容が食い違わないようにする。

```bash
git push -u origin <branch>
gh pr create --title "<type>: <英語の説明> (<タスクID>)" --body-file <本文のファイル>
```

- タイトルは英語、末尾に `(<タスクID>)` を付ける（手順3で、タスクとPRを結び付けるのに使う）。
- 本文は日本語で、次の構成にする（PR #7 の形）：

```markdown
## 概要

タスク **<ID>**（<タスク名>）。定義は `docs/tasks/<file>.md`、実装計画は `.claude/PRPs/plans/<file>.plan.md`。
<目的を1〜2文で>

## 変更内容

- **<まとまり>**：<内容>

## 画面の変更

<pnpm screenshots の出力。画面が変わらなければ「画面の変更なし」>

## 判断したこと

| 項目 | 判断 | 理由 |
|---|---|---|

## 分かったこと（後のタスクの材料）

- <発見と、どのタスクの定義に書き足したか>

## テスト

- [x] `pnpm lint`
- [x] `pnpm typecheck`
- [x] `pnpm test`（カバレッジ：全体 xx%）
- [x] `pnpm build`
- [x] <完了条件ごとの確認>
- [ ] <レビュアーに確かめてほしいこと>
```

判断や発見がなければ、その節は「なし」と書く（省略すると、検討しなかったのか、なかったのかが分からない）。

## 9. 報告する

- PRのURL、タスクID、残した判断事項
- 手順2で削除・保留したブランチ
- 着手できる手作業が残っていれば、その一覧
- マージ後に次に着手できるタスク（マージ後に `next-task` を実行すると、このタスクの状態を「完了」に直してから次へ進む）
