# next-task：次のタスクに着手してPRを作る

このリポジトリは、開発計画のタスクを **1タスク＝1ブランチ＝1PR** で進める（`docs/development-plan.md` 1.2）。
このスキルは、その手順を毎回同じように行うためのもの。各手順の「なぜ」を書いてあるので、
想定外の状況では理由に照らして判断する。

ユーザーへの確認は、`AGENTS.md` のとおり**推奨案と理由を付けて**聞く（Claude Code では AskUserQuestion を使う）。
スクリプトはこのファイルと同じディレクトリの `scripts/` にある（以下 `<skill>/scripts/`）。

## 1. main に切り替えて最新にする

```bash
git status --porcelain
git switch main && git pull --ff-only
```

- 作業ツリーに変更があれば、**切り替える前に止めて**ユーザーに確認する。変更を失わないため。
  推奨は「今のブランチにコミットする」（理由：stash は忘れられやすい）。
- `--ff-only` が失敗したら（main にローカルだけのコミットがある）、止めて状況を伝える。main には直接 push しない決まりなので、何かがおかしい。

## 2. ローカルブランチを片付ける

```bash
bash <skill>/scripts/branches.sh
```

main 以外のブランチを、紐づくPRの状態で分類して出す（`git fetch --prune` も行う）。

| action | 状況 | すること |
|---|---|---|
| `delete` | PRがマージ済み・クローズ済みで、PRの後のコミットがない | 確認せずに `git branch -D <branch>` |
| `ask` | PRがない | 削除するか保留するかを確認する |
| `ask` | PRがオープン中 | 同上。レビュー対応中の作業があることが多い |
| `ask` | マージ済み・クローズ済みだが、PRの後にローカルだけのコミットがある | 同上。消すと戻せない |

- `-D` を使うのは、squash マージだと `-d` が「マージされていない」と判断して失敗するため。PRの状態で確かめてあるので安全。
- `ask` のブランチは、まとめて1回で確認する。推奨の目安：
  - `local_only` が 0（コミットがすべてリモートにある）→ 削除を推奨（リモートから戻せる）
  - `local_only` が 1 以上 → 保留を推奨（消すと戻せない）
  - オープン中のPR → 保留を推奨
- 「削除」と答えたブランチだけを `git branch -D` で消す。消したブランチと残したブランチを一覧で報告する。

## 3. タスクを選ぶ

```bash
python3 -I <skill>/scripts/task_status.py
```

計画の表（状態）・`docs/tasks/*.md`（依存関係）・GitHub のPRを突き合わせて、実際の状態を出す。
PRは、ブランチ名に `/<ID>-` を含むか、タイトルに `<ID>` を含むものをそのタスクのPRとみなす
（だから手順4・8の命名規則を守る）。

- **タスクIDを指定された**：依存がすべて完了しているか確かめる。終わっていない依存があれば、どれが残っているかを伝えて確認する。
- **指定されていない**：「着手できる」から選ぶ。
  - 1つだけならそれに着手する。
  - 複数あれば確認する。推奨は表の上にあるもの（理由：計画の順番は、後のタスクの依存が早く解ける順になっている）。並行できるタスクは計画の第4章を見る。
- 「作業中」のタスクがあれば、選ぶ前に伝える。別のセッションで進めているかもしれない。
- 「着手できる手作業」（例：T0-05）は、オーナーの作業なのでPRは作らない。残っていることを報告にだけ書く。
- 「依存関係の補足」があれば読み、部分的な制約（例：「ブランチ保護だけは T0-04 の後」）を計画に反映する。
- T5-05（残りの46県）は県ごとにPRをくり返すので、マージ済みのPRがあっても「完了」とは限らない。表の状態を正とする。

## 4. ブランチを作り、計画の状態を更新する

ブランチ名は `<種別>/<タスクID>-<英語の短い説明>`（例：`chore/T0-02-component-e2e-tools`）。

```bash
git switch -c <種別>/<タスクID>-<slug>
```

`docs/development-plan.md` 第3章の表を直す：

- スクリプトの「計画を「完了」に直す」にあるタスク → `完了`。main に直接 push できないので、状態だけを直すPRを別に作らず、ここでまとめて直す。
- これから着手するタスク → `作業中`。

この変更を最初のコミットにする：`docs: <完了にしたID> を完了、<着手するID> を作業中にする`。

## 5. 読んで、実装計画を作り、承認を取る

読むもの（全部読んでから計画する。後から読むと手戻りになる）：

1. `docs/tasks/` のタスクの定義（目的・参照仕様・実装内容・完了条件・テスト条件・依存関係）
2. 参照仕様に挙がった `docs/development-overview.md` の章・要件ID・決定事項（D）・未決事項（U）
3. `docs/development-plan.md` 第4章（未決事項）で、「決めるタスク」がこのタスクの行。推奨案と理由が書いてある
4. Next.js のコードを書くなら、`node_modules/next/dist/docs/` の該当する章（`AGENTS.md`）

実装計画を `.plan.md` に書く（Claude Code では `/prp-plan` で作れる。`.claude/PRPs/plans/` に保存される）。少なくとも次を入れる：

- 先に書くテスト：テスト条件を1つずつ、テストのファイルとテスト名（要件IDを入れる）に落としたもの
- 作る・変えるファイルと、その順番
- 完了条件を1つずつ、どう確かめるか
- **判断が必要な点**：未決事項、仕様と実際が違いそうな点、版の選び方など。それぞれ推奨案と理由を付ける

ここで**止まって承認を取る**。計画の要点と判断が必要な点を示す。
コードを書く前にオーナーが方向を確かめられるようにするため（`docs/development-plan.md` 1.3）。
修正を求められたら計画を直し、もう一度確認する。

## 6. TDD で実装する

承認された計画のとおりに進める（`.claude/rules/testing.md`）。

1. テスト条件のテストを書き、**失敗することを確かめる**（Red）。失敗を見ないと、テストが本当に振る舞いを確かめているかが分からない。
2. 通る最小の実装を書く（Green）。
3. 整える（Refactor）。イミュータブル、小さな関数、境界での入力検証（`.claude/rules/coding-style.md`）。

- 1ファイルのテストは `pnpm vitest run <path>`、全体とカバレッジは `pnpm test`。
- Claude Code の Bash では、pnpm の前に `source ~/.nvm/nvm.sh && nvm use` が必要（`CLAUDE.md`）。
- 仕様・タスクの定義と実際（ライブラリの挙動、データの中身など）が違ったら、`docs/development-plan.md` 1.3 に従う。
  オーナーの判断が必要なものは確認し、採用した内容で仕様とタスクの定義を**同じPRで**更新する。
- 後のタスクに関係する発見（例：T0-01 で分かった `out/` の構成）は、該当するタスクの定義に書き足し、PRの「分かったこと」にも書く。
- コミットは区切りのよいところで、`<type>: <日本語の説明>` の形式で。

## 7. 完了条件を確かめ、レビューする

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm build
pnpm test:e2e   # 導入済み（T0-02 以降）なら
```

- タスクの定義の完了条件を1つずつ確かめる。コマンドで確かめられないもの（例：「カバレッジが基準を下回ると失敗する」）は、実際に試して結果を記録する。
- 共通の完了条件（`docs/development-plan.md` 1.1）：上のコマンドが通る、カバレッジが基準以上、レビューで CRITICAL・HIGH の指摘がない。
- コードレビュー（Claude Code では code-reviewer エージェント）を行い、CRITICAL・HIGH を直す。MEDIUM もできるだけ直す。
- 失敗したまま先に進まない。hooks や検査を回避しない（`--no-verify` は使わない）。

## 8. PRを作る

```bash
git push -u origin <branch>
gh pr create --title "<type>: <英語の説明> (<タスクID>)" --body-file <本文のファイル>
```

- タイトルは英語、末尾に `(<タスクID>)` を付ける（手順3で、タスクとPRを結び付けるのに使う）。
- 本文は日本語で、次の構成にする（PR #7 の形）：

```markdown
## 概要

タスク **<ID>**（<タスク名>）。定義は `docs/tasks/<file>.md`。
<目的を1〜2文で>

## 変更内容

- **<まとまり>**：<内容>

## 判断したこと

| 項目 | 判断 | 理由 |
|---|---|---|

## 分かったこと（後のタスクの材料）

- <発見と、どのタスクの定義に書き足したか>

## テスト

- [x] `pnpm lint`
- [x] `pnpm typecheck`
- [x] `pnpm test`（カバレッジ：全体 xx%）
- [x] `pnpm build`
- [x] <完了条件ごとの確認>
- [ ] <レビュアーに確かめてほしいこと>
```

判断や発見がなければ、その節は「なし」と書く（省略すると、検討しなかったのか、なかったのかが分からない）。

## 9. 報告する

- PRのURL、タスクID、残した判断事項
- 手順2で削除・保留したブランチ
- 着手できる手作業が残っていれば、その一覧
- マージ後に次に着手できるタスク（マージ後に `next-task` を実行すると、このタスクの状態を「完了」に直してから次へ進む）
