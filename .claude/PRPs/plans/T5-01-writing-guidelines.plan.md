## 方針

### 1. `content/guidelines/writing.md`（執筆ルール）

読む人：生成エージェント（T5-02 のスキルがこの文書を読み込む）とレビュアー。設計書の該当する章を写すだけにせず、「どう書くか」を例で示す。設計書と食い違わないように、数値（文字数の範囲）は 7.3 を正とし、この文書には表を載せたうえで「7.3 と `LENGTH_RANGES` が正」と書く。

構成：

1. この文書の位置づけ（設計書 7.2・7.3・9.3 の具体化。食い違ったら設計書が正。CI で見るもの・人が見るものの一覧）
2. 書く順番（9.2：おとな向けの日本語と出典で事実を確定 → こども向けの日本語・英語・中国語を派生。派生版で新しい事実を加えない）
3. 出典（9.3：実際に開いて確かめたURLだけ・優先順位・`title` はページの表記のまま・`accessed` は開いた日・確かめられなければ `sources: []`・写さず要約）
4. モードごとの書き方
   - おとな向け：事実を1つ加える（時期・地域・由来・数値）。「です・ます」。
   - こども向け：小学校中学年が読める語。理由や体験（何がすごいか、どう楽しむか）が中心。「〜だよ」などの話し言葉（判断1）。
5. 言語ごとの書き方
   - 日本語：漢字にはすべてふりがな（7.2 の記法と細かいルール。固有名詞の読みは公式の表記で確かめる）。
   - 英語：同じモードの日本語の意味を訳す。地名はマクロンなしのヘボン式（7.4.1 と `name.en` にそろえる。判断2）。日本語の語（ikura など）は、短い説明を添える。
   - 中国語：簡体字（D7）。日本の固有名詞は、中国語で定着した表記があればそれを使う。
6. 文字数（7.3 の表と数え方。範囲の外は警告だが、範囲に収めるのを基本にし、収めない理由があればPRに書く）
7. 名前・絵文字（`name` は短く。絵文字は1つで、古い端末でも表示される版のもの。判断3）
8. 避けること（宣伝・特定の店や商品、断定できない「日本一」など出典にない最上級、季節が限られるのに通年のように書くこと、画像）
9. 良い例・悪い例：名物・名所 × こども・おとな × 3言語の良い例と、よくある誤りごとの悪い例（出典にない事実の追加、逐語訳、こども向けの難しい語、宣伝、ふりがなの誤り、文字数の超過）。悪い例には「なぜ悪いか」と直した例を付ける。

例の題材：フィクスチャと同じく、広く知られた一般的な事実（例：北海道のじゃがいも）にする（判断4）。例はすべて、実装のときに `countLength`・`checkRuby` で文字数とふりがなを確かめる（良い例は範囲内・誤りなし、悪い例は意図した誤りだけ）。

### 2. `content/guidelines/review-checklist.md`（レビュー基準）

読む人：コンテンツレビュアー（9.4）と、それを手伝う検証エージェント。

構成：

1. レビューの流れ（9.2 の⑥〜⑧。PR を開く → プレビューで見る → 全件をチェックリストで確かめる → Suggested changes で直す → 承認 → オーナーが `status` を直して merge。判断5）
2. プレビューの開き方
   - PR のプレビューURL（PR のコメントに出る。Access でメールのワンタイムPINでログイン）。T0-06 で確定するので、決まっていない点は「T0-06 で確定」と書く（判断6）。
   - 手元で見る方法（`BUILD_TARGET=preview pnpm dev`）。
   - 「下書き」の印・こども／おとな・ふりがな・言語の切り替え方。
3. CI に任せてよいこと（記法・読みの字・`id`・日付などの誤り）と、CI の警告を確かめること（ふりがなのない漢字・文字数・出典なし）
4. チェックリスト（項目ごと・言語ごとにチェックボックス）：事実、出典、文字数、ふりがな、表現の適切さ、翻訳。それぞれ「何を見るか」「よくある誤り」を書く。
5. Suggested changes での直し方（行を選んでコメント → 提案の書き方 → まとめてレビュー（Start a review）→ 承認／変更を求める。YAML の行の折り返し（`>-`）とふりがなの記法を壊さない注意）
6. 承認の基準（すべての項目を確かめた・事実と出典の食い違いがない・警告には理由がPRにある）

## 判断が必要な点

| # | 点 | 推奨 | 理由 |
|---|---|---|---|
| 1 | こども向けの日本語の文体 | 話し言葉（「〜だよ」「〜なんだ」）。おとな向けは「です・ます」 | フィクスチャがこの形で、カードの上でモードの違いがすぐ分かる。「です・ます」にそろえると、こども向けとおとな向けの差が語の難しさだけになり、読み分けにくい |
| 2 | 英語の地名の書き方 | マクロンなしのヘボン式（Kyoto、Tokyo）。`name.en` と 7.4.1 にそろえる | 同じカードの中で表記がそろう。マクロンは一般の英語の文章でほとんど使われない |
| 3 | 使ってよい絵文字の範囲 | Emoji 12.0（2019年）までに入った絵文字。ZWJ の組み合わせ・国旗は使わない。実装のときに、対応環境（5.3）の端末で表示される範囲を公式の一覧で確かめてから書く | Windows 10 の Edge の標準の絵文字フォントは、それより新しい絵文字を表示しないと見込まれる（学校の端末に Windows がある。D25）。ZWJ・国旗は OS によって2つの絵文字に分かれて見える |
| 4 | 例の題材 | フィクスチャと同じ北海道（じゃがいも・牛乳など）の一般的な事実にし、「書き方の例。出典を確かめた内容ではないので、コンテンツに写さない」と書く | 本物の県のコンテンツはまだない。例のために出典を調べるのは T5-04 の作業と重なる。注意書きで、生成エージェントが例を事実として写すのを防ぐ |
| 5 | `status` を `reviewed` にするのは誰か・いつか | レビュアーの承認の後、オーナーが（Claude Code に頼んでもよい）同じPRで `verified` → `reviewed` にするコミットを足してから merge する。レビュアーは内容の確認と承認だけをする | 承認（人が確かめた記録）は PR に残る。レビュアーが `status` を直すと、Suggested changes の数が増え、確認していない項目まで `reviewed` にする誤りが起きやすい。9.2 の図の「⑧ オーナーが merge／status: reviewed」とも合う |
| 6 | プレビューURLの開き方（T0-06 が未着手） | 設計どおりの手順（PR のコメントのURL → Access のワンタイムPIN）を書き、決まっていない所に「T0-06 で確定」と印を付ける。T0-06 のタスクの定義に、確定したらこの節を直すことを足す。手元で見る方法（`BUILD_TARGET=preview pnpm dev`）も書く | T5-04 で使うまでに T0-06 が終わるので、そこで直せば足りる。T0-06 を待つと T5-02 の着手が遅れる |
| 7 | 例文の文字数・ふりがなの確認 | 一度だけのスクリプトで確かめ、結果を PR に書く。テストとしてはコミットしない | タスクの定義で自動テストはないとしている。文書の例を抜き出して検査するテストは、Markdown の書き方に依存して壊れやすい |
