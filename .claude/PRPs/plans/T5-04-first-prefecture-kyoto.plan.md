# T5-04 1県目（試行）：実装計画

- タスクの定義：`docs/tasks/m5-content.md` の T5-04
- ブランチ：`feat/T5-04-first-prefecture-kyoto`
- 参照仕様：開発概要書 第9章（9.2 の①〜⑧、9.3、9.4）、`content/guidelines/writing.md`・`review-checklist.md`、スキル `gotouchi-content`

この計画は、PR で実際に作った内容に合わせて直してある（①〜⑥まで。⑦・⑧の結果は、レビューの後に書き足す）。承認したときから変えた点は、末尾の「承認後に変えたこと」にある。

## 目的

1県（京都府）で制作の流れ（9.2 の①〜⑧）を最後まで通し、ほかの46県に広げる前に問題を直す。

## 着手時に分かっていること

- `content/prefectures/26-kyoto.yaml` は基本情報だけ（`specialties: []`・`spots: []`・`access` なし）。
- 本番に出るのは、`isComplete`（行き方があり、名物・名所が1件以上あり、すべて `reviewed`）の県だけ（`docs/architecture/card.md`）。**行き方を書かないと、京都府は本番で「準備中」のまま**。
- スキーマ：名物・名所はちょうど3件か空。`access` は任意だが、書くなら `emoji`・`mode`・`route`・`durationMin`・`sources`・`status` が必須。
- `tests/data/content.test.ts` の「T1-08: 名物・名所は空で、行き方はない（未作成）」は、このタスクで外す（定義の実装内容）。
- **レビュアーの Team `maps-reviewers` は、今メンバーが0人で、招待中の人もいない**（`gh api` で確かめた）。⑦（レビュアーの承認）を行う人がいない（判断1）。
- `main-review` のルールセット：CODEOWNERS（`/content/prefectures/` は `@vivastack-labs/maps-reviewers`）の承認が1件必要。オーナーはバイパスで merge できる。
- T5-02 の試行（京都府の①〜④。YAML はコミットしていない）で、決めることが4つ残っている（判断2〜5）。
- プレビューは、オーナーが `preview` のデプロイを承認すると、`https://pr-<番号>-maps.vivastack-dev.workers.dev/ja/` に出る（T0-06）。プレビューのビルドでは、`reviewed` でない項目に「下書き」の印が付く。

## 進め方

1. **①〜④（スキル `gotouchi-content`）**：メインのセッションでスキルを動かす（②・④の検証エージェントと `web-fetch` を呼ぶため、サブエージェントには任せられない）。始めと終わりの時刻、手順ごとの時間、指摘の件数を記録する。
2. **テストの整理**：`tests/data/content.test.ts` の T1-08 の「未作成」のテストを外す。ほかのデータの検査（件数・全言語・文字数・ふりがな）が、京都府の中身で通ることを確かめる。
3. **検査**：`pnpm content:validate`・`pnpm lint`・`pnpm typecheck`・`pnpm test`・`pnpm build`・`pnpm build:preview`、E2E は手元で `pnpm test:e2e`（E2E のビルドはフィクスチャなので京都府の中身には関係しないが、データの変更で壊れていないことを確かめる）。
4. **⑤ PR**：`status: verified` で PR を出す。本文に、項目ごとの出典・要確認の読み・行き方の時間の内訳・かかった時間を書く。
5. **⑥**：オーナーが `preview` を承認 → プレビュー URL で京都府のカード（3言語・2モード・下書きの印）を確かめる。スクリーンショットは、プレビューのビルドで京都府を選んだカードを撮る（判断7）。
6. **⑦ レビュー**：判断1のとおり。レビューの指摘を取り込む（`review-checklist.md` 5.）。
7. **⑧**：承認の後、オーナーの依頼で `status` を `reviewed` にするコミットを足し、オーナーが merge する。merge の後、本番で京都府のカードが出ることを確かめる。
8. **振り返り**：分かった問題を、スキル・エージェント・`writing.md`・`review-checklist.md` に反映する（判断6）。`review-checklist.md` 5. の「画面の名前は、T5-04 の試行で確かめて直す」を、実際の画面で直す。かかった時間と問題を、`docs/tasks/m5-content.md` の T5-04（と T5-05 の見込み）に記録する。

## 判断が必要な点

| # | 項目 | 推奨 | 理由 |
|---|---|---|---|
| 1 | ⑦ のレビュアー | オーナーが、レビューを頼める人を `maps-reviewers` に招待する。招待できるまでの間に①〜⑥を進め、PR はレビュー待ちで開けておく。すぐに頼める人がいなければ、**この試行だけ**オーナーがレビュアーを兼ね（チェックリストで確かめ、PR にコメントで結果を残す）、バイパスで merge する。兼ねた場合は、「承認と merge を別の人にする」（9.4）を満たしていないことを PR とタスクの定義に書く | ⑦ は試行で確かめたい手順の中心で、人がいないと完了条件を満たせない。一方で、①〜⑥と振り返りは人を待たずに進められる。兼ねるのは、47県に広げる前にレビュアーを決めることを前提にした例外にする |
| 2 | 行き方の所要時間の出典 | (a) 交通機関の公式の、固定のページ（JR 東海・JR 西日本の、東京〜京都の所要時間を書いたページ・駅の時刻表の PDF など）を探す。(b) 見つからなければ、オーナーが公式の時刻の検索で東京→京都の時間を確かめて数字をもらい、`sources: []` にして、PR とコメントに「オーナーが公式の検索で確かめた（日付）」と書く | 行き方がないと本番で「準備中」のまま（`isComplete`）。writing.md 8 は「交通機関の公式の情報の数字」で、出典にない時間を見積もらない。第三者のサイト（駅探など）は出典にしない。検索の結果のページは固定の URL でなく、「開いて確かめた出典」にできないので、(b) は出典なしの扱いにする |
| 3 | 照合・検証の回数の上限（2回） | 2回のままにし、**2回目の後に残ったのが「要確認」だけ（誤りがない）なら、3回目を1回だけ許す**。誤りが残ったら `draft` のまま | T5-02 の試行で、2回目の後に残ったのは直し方の簡単な要確認だった。`draft` が残ると、その項目は `reviewed` にできず、県が本番に出ない。誤りは毎回見つかっているので、誤りに3回目は許さない（回り続けるのを防ぐ） |
| 4 | 「要確認」の扱い | 誤り（出典と違う数字・足した事実・読みの誤り）は必ず直す。要確認は、メインのセッションが読んで、直せば明らかによくなるものだけを直し、直さないものは理由を PR に書いて、レビュアーの判断に回す | 要確認は、呼び直すと出たり出なかったりする（T5-02）。すべてに対応すると回数の上限に当たり、判断の基準も揺れる。最後に人（レビュアー）が全件を見るので、そこに渡す |
| 5 | かかった時間の記録 | ①〜④の手順ごと、⑥の承認待ち、⑦のレビュー、⑧ を、時刻で PR とタスクの定義に記録する。T5-05（46県）の見込みも書く | 定義の「かかった時間と、見つかった問題を記録する」。46県の計画（1日何県か）に使う |
| 6 | 振り返りの反映を同じ PR にするか | 同じ PR にする（スキル・エージェント・ルール・チェックリストの直し）。ただし、エージェントの指示を直して `evals/` の評価をやり直すほど大きくなるなら、続く PR に分ける | 定義は「同じPRか、続くPRで」。小さな直しは、何を見つけて直したかを1つの PR で読めるほうがよい。評価のやり直しは時間がかかり、レビューの対象（コンテンツ）と混ざる |
| 7 | スクリーンショット | プレビューのビルドで京都府を選んだカード（ja のおとな・こども）を撮り、PR に載せる。撮る画面は `tests/screenshots/pages.spec.ts` の `SCENES` に足さない（スクリーンショットのビルドはフィクスチャのコンテンツなので、京都府の中身が出ない） | 画面の部品は変わらないので、`pnpm screenshots` の対象ではない。レビュアーはプレビュー URL で見る。PR の記録としては、プレビューの URL と、撮った画像があれば足りる |
| 8 | 名物の3つ目 | 京漬物と八ツ橋のうち、①で公式の出典を確かめられたほう。両方確かめられたら京漬物 | 八ツ橋は特定の店の商品と結びつきやすく、writing.md 9（宣伝を避ける）に触れやすい |

## 実際の結果（①〜⑥）

- 名物：西陣織（京都府の伝統的工芸品のページ）・宇治茶（農林水産省「にっぽん伝統食図鑑」）・京漬物（同）。名所：清水寺（公式の「歴史」「巡る」）・伏見稲荷大社（公式の「伏見稲荷大社とは」「大社マップ」）・天橋立（天橋立観光協会）。八ツ橋は使わなかった（判断8）。
- 行き方：東海道新幹線 東京駅 → 京都駅、134分。出典は JRおでかけネットの「のぞみ25号」の列車時刻表（東京始発・毎日運転。10:30 → 12:44）。判断2の (a) で見つかったので、オーナーに時間を確かめてもらう (b) は要らなかった。
- 照合（②）：1回目は要確認3件（題名の「／」、宇治茶の文が出典の写しに近い、「参拝者」と「崇敬者」）・誤り0件。2回目は指摘なし。
- 検証（④）：1回目は要確認6件（訳の不自然さ・「など」の抜け・主語のかかり方）・誤り0件。2回目は指摘なし。3回目は要らなかった（判断3）。
- かかった時間：①〜④で約13分（16:08〜16:21）。
- 検査：`content:validate`（誤り・警告0件）、`lint`、`typecheck`、`test`（2048件、カバレッジ 96.7%）、`build`（京都府は本番で「準備中」のまま＝`verified` なので正しい）、`build:preview`（京都府のカードに下書きの印）、手元の `test:e2e`（1978件が成功）。
- T1-08 の未作成のテストは、京都府を書いた状態で落ちること（`expected [ '26' ] to deeply equal []`）を確かめてから外した。
- コードレビュー：HIGH 1件（行き方の出典の日付つき URL は、日付が過ぎると中身のないページになる）を直した。MEDIUM 2件（スキルの「通った」の意味、writing.md 8 の範囲と列車の選び方）を直した。LOW のうち、清水寺の英語名（公式サイトの表記のまま）と suguki の説明（足すと新しい事実になる）は直さず、PR でレビュアーの判断に回す。
