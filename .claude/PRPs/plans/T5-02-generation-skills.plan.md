# T5-02 生成スキルと検証エージェント：実装計画

- タスクの定義：`docs/tasks/m5-content.md` の T5-02
- ブランチ：`feat/T5-02-generation-skills`
- 参照仕様：開発概要書 7.1〜7.3、9.2、9.3、D22、`content/guidelines/writing.md`・`review-checklist.md`（T5-01）

## 目的

開発概要書 9.2 の①〜④（おとな向けの日本語と出典の下書き → 出典との照合 → 派生版の生成 → 派生版の検証）を、毎回同じ手順と品質で実行できるようにする。

## 着手時に調べたこと

- **形態素解析のツール**（7.2 のふりがなの自動付与）：npm の候補を、スクラッチパッドで実際に動かして比べた（6文。清水寺・函館山・羽田空港・新千歳空港・西陣織・八ツ橋など）。
  - `kuromoji`（0.1.2、最終更新 2022年、41MB、IPADIC）と `lindera-wasm-nodejs-ipadic`（2.0.0、2026年1月、13MB、IPADIC を同梱した WASM）は、同じ辞書なので同じ結果。清水寺（きよみずでら）・羽田空港（はねだくうこう）・西陣織（にしじんおり）・八ツ橋（やつはし）は正しい。函館山は「はこだてさん」と誤る。
  - `lindera-wasm-nodejs-unidic`（UniDic）は、固有名詞を誤る（清水寺→しみずてら、羽田→はた）。`reading` は終止形の読み（行き→いく）なので、そのままでは使えない。
  - `lindera-wasm`（無印）は Web 向けで、辞書を OPFS から読む。Node.js では `lindera-wasm-nodejs-*` を使う。
  - `sudachi-wasm333`（非公式、125MB）、`mecab-wasm`（2022年）は外した。
  - インストールスクリプトはどれもない（`pnpm-workspace.yaml` の `allowBuilds` に足さなくてよい）。
- 既存のスキル・エージェントに `gotouchi-` で始まるものはない（D22 の名前の決まりに合う）。
- このセッションのメインには WebFetch がなく、`web-fetch` エージェントが代わりをする。`task-implementer` は Web を使えず、ほかのエージェントも呼べない。→ 試行（1県分の①〜④）と、誤りを入れた YAML の検証は、メインのセッションで行う。
- `content:validate` は `CONTENT_DIR`（既定 `content/prefectures`）の YAML を読む。テストは `tests/unit/scripts/` に、`scripts/` と同じ名前で置く。カバレッジの対象に `scripts/**` が入る。

## 方針

### 1. ふりがなの自動付与：`pnpm content:furigana`（コード。TDD）

- `scripts/lib/furigana.ts`（純粋な関数。トークナイザーは引数で受け取る）：
  - `alignReading(surface, reading)`：語の表記と読み（カタカナ）を、送り仮名で区切って `{漢字|よみ}` の並びにする（`町並み`／`マチナミ` → `{町並|まちな}み`、`焼き魚`／`ヤキザカナ` → `{焼|や}き{魚|ざかな}`）。合わせられないときは、語全体を1つのルビにする。
  - `annotate(text, tokenize)`：文のうち、ふりがなの付いていない漢字を含む語にだけふりがなを付ける。すでにある `{…|…}` はそのまま残す。読みのない語（辞書にない語）は、そのまま残して報告する。
  - 固有名詞（品詞が「固有名詞」）と、辞書にない語・合わせられなかった語を「要確認」の一覧として返す。
- `scripts/furigana.ts`（CLI）：標準入力の各行（または引数）にふりがなを付けて標準出力に出し、要確認の一覧を標準エラーに出す。トークナイザーは `lindera-wasm-nodejs-ipadic`。
- YAML のファイルを直接は書き換えない（判断2）。

### 2. スキル：`.claude/skills/gotouchi-content/SKILL.md`

1県（引数：県コードか `id`。項目を指定すれば、その項目だけ）について、次を順に行う。最初に `content/guidelines/writing.md` を読む。

1. **① 下書き**：名物3・名所3・行き方を選び、Web で出典を探して**実際に開いて**読み、おとな向けの日本語と出典を書く。日本語は `pnpm content:furigana` でふりがなを付け、要確認の語の読みを公式の表記で確かめる。`status: draft`。
2. **② 照合**：`gotouchi-source-checker` エージェントに渡す。指摘を直し、もう一度照合する（2回まで）。確かめられない出典は外し、確かめられる出典がなければ `sources: []`。
3. **③ 派生版**：おとな向けの日本語から、こども向けの日本語・英語・中国語を作る（新しい事実を足さない。writing.md 2・4・5）。
4. **④ 検証**：`gotouchi-derivative-checker` エージェントに渡し、指摘を直す（2回まで）。
5. `pnpm content:validate` を誤りなしで通す。②と④を通った項目を `status: verified` にする。通らなかった項目は `draft` のまま残し、理由を報告する。
6. 報告：項目ごとの状態、残った警告と理由、要確認の読み、かかった時間（T5-04 の記録に使う）。

Web のページを開くときは WebFetch を使う。使えない環境では `web-fetch` エージェントに頼む。

### 3. エージェント（ファイルを書き換えず、決まった形の報告を返す）

- `.claude/agents/gotouchi-source-checker.md`（②）：項目ごとに、出典の URL を実際に開き、おとな向けの日本語の事実（数字・時期・名前・場所・由来）が出典に書かれているかを照合する。出典の文の写しになっていないか、出典の優先順位（9.3）、`accessed` も見る。ツールは Read・Grep・Glob・WebFetch。
- `.claude/agents/gotouchi-derivative-checker.md`（④）：派生版（こども ja・en・zh）が同じ項目のおとな向けの日本語と同じ事実か（足した事実・抜けた事実）、モードの書き分け、翻訳の自然さ・簡体字・英語の表記の決まり、ふりがなの読み（固有名詞を含む）を見る。`pnpm content:validate` を実行して、誤りと警告も報告に入れる。ツールは Read・Grep・Glob・Bash。
- 報告の形：`項目のパス｜重さ（誤り／要確認）｜何が違うか｜根拠（出典の該当する文など）｜直し方`。

### 4. 誤りを入れた YAML での検証（評価）

- 試行で作った1県の YAML に、わざと誤りを入れた写しを作る：出典と違う数値、派生版で足した事実、ふりがなの読みの誤り（記法は正しい）、文字数の超過。
- 2つのエージェントに渡し、すべてが指摘されるかを確かめる。結果を PR に書く。
- 誤りを入れた YAML と、指摘されるべき一覧を `.claude/skills/gotouchi-content/evals/` にコミットする（判断6）。

## 先に書くテスト

`tests/unit/scripts/furigana.test.ts`（テスト名に「7.2」を入れる）：

- 7.2 送り仮名を括弧の外に出す：`見える`→`{見|み}える`、`町並み`→`{町並|まちな}み`、`焼き魚`→`{焼|や}き{魚|ざかな}`
- 7.2 読みのカタカナをひらがなにする。長音「ー」は残す
- 7.2 漢字のない語（ひらがな・カタカナ・数字・記号）にはふりがなを付けない
- 7.2 すでにある `{漢字|よみ}` は変えない（同じ文の中の、付いていない漢字にだけ付ける）
- 7.2 読みと表記を合わせられないときは、語全体を1つのルビにして、要確認に入れる（`八ヶ岳` のように、カタカナが間に入る語）
- 7.2 辞書にない語（読みがない）は、そのまま残して、要確認に入れる
- 7.2 固有名詞を要確認に入れる
- 7.2 出力は `checkRuby` で誤りなし（実際の辞書で、文をいくつか通す）
- CLI：標準入力の各行を変換し、要確認の一覧を標準エラーに出す。空の入力でも失敗しない

## 判断が必要な点

| # | 点 | 推奨 | 理由 |
|---|---|---|---|
| 1 | 形態素解析のツール | `lindera-wasm-nodejs-ipadic`（2.0.0、devDependency） | 試した6文で `kuromoji` と同じ結果（同じ IPADIC）。サイズが3分の1（13MB と 41MB）で、更新が続いている（2026年1月と 2022年）。同期の API で使いやすい。UniDic は固有名詞の読みを誤った。インストールスクリプトがない |
| 2 | ふりがなの付け方の形 | 文を受け取って文を返す CLI（標準入力 → 標準出力）。YAML のファイルは書き換えない | `yaml` で読んで書き戻すと、1行のマップが `{ ja: … }`（括弧の内側に空白。yamllint の誤り）になり、長い行が折り返される（writing.md 11 に反する）。文だけを変換すれば、YAML の書き方はスキルが決まりどおりに書ける |
| 3 | スキルの分け方 | スキルは1つ（`gotouchi-content`。①〜④を順に行う。項目を指定して一部だけをやり直せる）。エージェントは2つ（②・④） | 47県で毎回1つのスキルを呼べば済む。定義の「①と③のスキル」は、同じスキルの中の手順として満たす。②（Web を開く）と④（Web を使わない）は、要るツールが違うので分ける |
| 4 | 検証エージェントのモデル | 2つとも `opus` | 検証は、判断の質が結果を左右し、出力が少ない（next-task でレビューを Opus にしているのと同じ理由）。T5-04 で1県あたりの時間と費用を測り、④は `sonnet` に下げられるかを決める |
| 5 | 指摘の直し方と `status` | エージェントは報告だけを返し、スキル（メイン）が直す。直して照合し直すのは2回まで。②と④を通った項目だけを `verified` にし、通らない項目は `draft` のまま残して報告する | 検証する側が直すと、自分の直しを自分で確かめることになる。回数に上限を付け、直らない項目を人に回す |
| 6 | 誤りを入れた YAML の扱い | `.claude/skills/gotouchi-content/evals/` にコミットする（誤りを入れた YAML と、指摘されるべき一覧） | T5-04・T5-05 でエージェントの指示を直したときに、同じ評価をやり直せる。中身は誤りを含むので、`content/` には置かない |
| 7 | 試行の1県 | 京都府で試し、YAML はこの PR にコミットしない（スクラッチパッドに残し、結果を PR に書く）。T5-04 で、直したスキルで作り直す | T5-04 の推奨と同じ県で、ルールの足りない所が早く見つかる。レビューを経ていないコンテンツを、スキルの PR に混ぜない |
| 8 | 要確認の読みの知らせ方 | `content:furigana` が、固有名詞・辞書にない語・合わせられなかった語を標準エラーに出す。スキルは、それらの読みを公式の表記で確かめる手順を持つ | 試した文で、函館山を「はこだてさん」と誤った。固有名詞の読みは辞書だけでは正しくならない（7.2「固有名詞はレビューで特に注意」） |
| 9 | Codex での使い方 | 対象にしない（`.claude/` だけに置く。D22） | D22 で置き場所を `.claude/` に決めている。Codex でも使うなら、別のタスクで `.agents/` に写す |
