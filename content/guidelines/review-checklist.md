# レビュー基準

コンテンツレビュアー（開発概要書 9.4）が、1県分のコンテンツ（1 PR）を確かめるときの手順と基準。検証エージェントがレビューを手伝うときも、同じ基準で見る。書き方の決まりは [writing.md](writing.md)（以下「執筆ルール」）にある。

## 1. レビューの流れ

開発概要書 9.2 の⑥〜⑧にあたる部分。

1. PR が開く。`status` は `verified`（検証エージェントが確かめ済み）。CI（`pnpm content:validate` を含む）とプレビューが動く。
2. **プレビューで、実際のカードの表示を見る**（2.）。
3. **全件**（行き方 1・名物 3・名所 3）を、4. のチェックリストで確かめる。
4. 直したい所は、PR の **Suggested changes** で提案する（5.）。
5. 全部を確かめたら、承認（Approve）する。直しが要るときは「変更を求める（Request changes）」にする。
6. 承認の後、**オーナーが** `status` を `verified` から `reviewed` にするコミットを同じ PR に足して、merge する。レビュアーは、内容の確認と承認だけをする（`status` は直さない）。

レビュアーの権限は Write。承認はレビュアー、merge はオーナーが行う（9.4）。

## 2. プレビューの開き方

### PR のプレビュー URL

- PR に、CI がプレビュー URL をコメントする。形式は `https://pr-<PR番号>-maps.vivastack-dev.workers.dev/ja/` の見込み（**T0-06 で確定**）。
- プレビュー URL は、Cloudflare Access で守られている。開くと認証の画面が出るので、**許可されたメールアドレスを入れ、届いたワンタイムの PIN を入力して**ログインする（**手順の詳細は T0-06 で確定**。許可されるのは、オーナーとレビュアーのメールアドレスだけ）。
- プレビューは、すべての状態の項目を出す。`reviewed` でない項目のカードには、**「下書き」の印**が付く。ページには `noindex` が付き、検索には出ない。

### 手元で見る

リポジトリを clone して、PR のブランチに切り替え、次を動かす（Node.js と pnpm が要る。手順は `README.md`）。

```bash
BUILD_TARGET=preview pnpm dev
```

`http://localhost:3000/ja/` を開く（3000番が使用中なら別の番号。端末に出る）。`BUILD_TARGET=preview` を付けないと、下書きの項目が出ず、「準備中」と表示される。

### 見る県を開く

- 地図の県をクリック（スマホではタップ）すると、カードが出る。`/ja/#pref-<県コード>`（例：京都府なら `#pref-26`）で、直接開ける。
- 県のカードは、JavaScript が動くと内容（行き方・名物・名所・出典）が出る。出ないときは、少し待つか、再読み込みする。

### 表示を切り替える

画面の上（ヘッダー）のボタンで、次を切り替えて確かめる。

| 切り替え | 見る所 |
|---|---|
| **こども／おとな** | 名物・名所の解説（モードごとに別の文）。行き方・出典はモードで変わらない |
| **ふりがな ON／OFF** | ON のとき、日本語の漢字の上に読みが出る。付け忘れ・読みの間違いが見つかる |
| **言語（日本語・English・中文）** | 英語・中国語の文。URL の `/ja/`・`/en/`・`/zh/` でも切り替わる |

県ごと・言語ごと・モードごとに、カードを開き直す必要はない。切り替えながら、全件を見る。

## 3. CI に任せてよいこと・人が確かめること

`pnpm content:validate` は PR の CI で動く。**誤り**は、ビルドが止まる。

### CI に任せてよい（誤りになる）

- ふりがなの記法（括弧の対応・読みが空・読みがひらがな以外）
- 英語・中国語の文のふりがなの記法
- ファイル名・`id` の重複
- 出典のタイトルの記法・存在しない確認日（`2026-02-30` など）
- YAML の形（項目の数・必須の項目・`status` の値）

### CI の警告を確かめる

警告は、ビルドを止めない。**警告が残っている項目は、直されているか、理由が PR に書かれているか**を確かめる。

- ふりがなのない漢字（日本語）
- 解説文の文字数・語数が範囲の外（執筆ルール 6.）
- 出典なし（`sources: []`）

CI のログに警告が出る。PR を開いたら、まず Checks で `content:validate` の警告の一覧を見る。

### 人にしか見つけられない

次は、CI を通っても間違えうる。チェックリスト（4.）で確かめる。

- ふりがなの**読みが合っているか**
- 事実が出典と合っているか
- 派生版（こども・英語・中国語）に、新しい事実がないか
- 語の難しさ・表現の適切さ・翻訳の自然さ・簡体字か

## 4. チェックリスト

項目ごとに確かめる。**対象は、行き方 1・名物 3・名所 3**。コピーして、PR のレビューのコメントに貼り、チェックを付けていく。

```markdown
### 行き方
- [ ] 事実：交通手段・経路・所要時間が、出典と合っている
- [ ] 出典：URL を開いて、内容が確かめられる。確認日がある
- [ ] ふりがな：経路の駅・空港の読みが合っている
- [ ] 表現：所要時間が「目安」として読める
- [ ] 翻訳：en・zh が ja と同じ意味で、駅・空港の名前が合っている

### 名物 1（名前：　　　）／名物 2／名物 3
- [ ] 事実（おとな ja）：出典と合っている。事実が1つある
- [ ] 出典：URL を開いて確かめられる／なければ `sources: []` で、警告の理由がある
- [ ] 文字数：警告がない（ある場合は理由が PR にある）
- [ ] ふりがな：こども・おとな・名前の読みが合っている。付け忘れがない
- [ ] 表現：こども向けは語がやさしい。宣伝・出典にない最上級・季節の抜けがない
- [ ] 翻訳：こども・おとなの en・zh が、同じモードの ja と同じ意味。新しい事実がない
- [ ] 絵文字：1つで、品物に合っている。表示される

### 名所 1／名所 2／名所 3
（名物と同じ。絵文字は付いていれば確かめる）

### 全体
- [ ] CI の警告に、すべて理由があるか、直してある
- [ ] 3モード・3言語・ふりがな ON／OFF で、カードが読める（文が切れていない、記号が崩れていない）
```

### 確かめ方と、よくある誤り

| 観点 | 何を見るか | よくある誤り |
|---|---|---|
| 事実 | おとな向けの日本語の事実を、出典のページで確かめる（URL を開く）。数字・時期・名前・場所 | 数字が違う（古い・別の年）。出典にない事実が混ざる。似た名前の別のものを書く |
| 出典 | URL が開く。内容が、書かれている事実を支えている。優先順位（公式 → 公的機関 → それ以外。執筆ルール 3.）。確認日が実際に開いた日 | 開いていない URL・トップページだけを書く。内容が違う。出典のタイトルがページの題名と違う |
| 文字数 | CI の警告。範囲（執筆ルール 6.）に収まっているか | 範囲を超える。理由がない |
| ふりがな | ふりがな ON で、日本語の全部の漢字に読みが付いている。読みを公式の表記と比べる（地名・人名・施設名・駅名） | 同じ字の読み違い（「秋」「市」「町」など、読みが複数ある字）。固有名詞の読み |
| 表現 | こども向けの語がやさしい。宣伝がない。「日本一」などの最上級が、出典にある。季節が分かる | 難しい語。特定の店の名前。出典にない順位。一年中あるように読める |
| 翻訳 | en・zh が、同じモードの ja と同じ意味。新しい事実がない。英語の地名がマクロンなしのヘボン式。中国語が簡体字 | 逐語訳で不自然。ja にない事実の追加。繁体字。ヘボン式でない地名 |

## 5. Suggested changes での直し方

直したい所は、PR の差分（Files changed）で、行にコメントして提案する。

1. PR の **Files changed** で、直したい行にカーソルを合わせ、`+` を押す（複数行は、ドラッグして選ぶ）。
2. コメントの欄の **Suggested change** のボタン（±のマーク）を押す。直したい内容が入った欄が出るので、**直した後の行**に書き換える。理由を、欄の外に1行書く。
3. **Start a review**（レビューを始める）で、まとめて出す。**Add single comment** は、その場で1件ずつ通知されるので、使わない。
4. すべて確かめたら、**Finish your review** で **Approve**（承認）か **Request changes** を選んで送る。

### YAML を壊さない注意

- 日本語の長い文は、`>-` で折り返してある（例：`adult: >-` の下に2行以上ある）。`>-` の文では、行の折り返しの改行が**空白1つ**になり、画面にも空白が出る。**折り返しは、読点（、）の後だけにして、語の途中で折り返さない**。折り返した行を直すときも、折り返しの形（`>-` と、行頭のインデント）を変えない。空白は、文字数には数えない（執筆ルール 6.）。
- ふりがなの記法 `{漢字|よみ}` の `{` `|` `}` を、消したり増やしたりしない。直した後に、括弧が対応しているかを見る。
- 直す文を、`"` で囲んである文では、`"` の中に `"` を書かない。
- 行頭のインデント（空白）を変えない。
- 提案が YAML として正しいかは、手元か CI の `pnpm content:validate` で分かる。提案の後に CI が失敗したら、PR に書く。
- 直しを受けるのは、PR の作者（Claude Code とオーナー）。Suggested changes は、**作者が取り込むか**、レビュアーが `Commit suggestion` で取り込む。取り込んだ後は、CI が通ることを確かめる。

## 6. 承認の基準

次のすべてを満たしたら、承認する。

- 4. のチェックリストを、**全件**（行き方 1・名物 3・名所 3）で確かめた。
- 事実と出典に、食い違いがない（食い違いは、直してから承認する）。
- CI の警告に、すべて直しがあるか、理由が PR にある。
- 直しの提案が、取り込まれたか、取り込まない理由がある。

確かめきれない項目（出典の URL が開かない、読みが調べても分からない、など）があるときは、承認せず、PR にコメントする。**確かめていない項目を、確かめたことにしない**。

承認の後、`status` を `reviewed` にして merge するのは、オーナー（Claude Code に頼んでもよい）。
