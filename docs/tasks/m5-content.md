項目の意味と進め方は [development-plan.md](../development-plan.md) の第1章、進み具合は第3章にある。参照仕様の章番号は [開発概要書](../development-overview.md) のもの。

マイルストーンの完了条件：全項目が `reviewed`。

T5-01〜T5-03 は M2・M3 と並行して進められる。

## T5-01 執筆ルールとレビュー基準

- **種別**：docs
- **依存関係**：T1-07
- **目的**：生成エージェント・検証エージェント・レビュアーが、同じ基準で書き、同じ基準で確かめられるようにする。
- **参照仕様**：7.2、7.3、9.3、9.4

### 実装内容

- `content/guidelines/writing.md`：7.2・7.3・9.3 のルールを、良い例・悪い例（こども向け・おとな向け、3言語）を付けて書く。
- `content/guidelines/review-checklist.md`：9.4 の確認範囲（事実、出典、文字数、ふりがな、表現の適切さ、翻訳）をチェックリストにする。プレビューURLの開き方と、Suggested changes での直し方も書く。

### 完了条件

- markdownlint が通る。
- オーナーとレビュアーが内容を確認した。

### テスト条件

- 自動テストはない（文書のため）。
- 確認の方法：T5-04 の試行で実際に使い、分かりにくかった点を直す。

## T5-02 生成スキルと検証エージェント

- **種別**：feat
- **依存関係**：T5-01
- **目的**：9.2 の①〜④を、毎回同じ手順と品質で実行できるようにする。
- **参照仕様**：9.2、9.3、7.1〜7.3、D22

### 実装内容

- `.claude/skills/` に生成用のスキル：
  - ①おとな向けの日本語と出典の下書き（Web検索、出典ページを実際に開いて確認する）。
  - ③派生版（こども向けの日本語、英語、中国語）の生成。新しい事実を加えない。
- `.claude/agents/` に検証用のエージェント：②出典ページと内容の照合、④派生版とおとな向けの日本語の一致、文字数、ふりがな。
- 名前は既存のスキル・エージェントと重ならないようにする（例：`gotouchi-` を付ける。D22）。
- ふりがなの自動付与（7.2）：形態素解析のツールを選ぶ（推奨：pnpm で入るもの。Python など別の実行環境を増やさないため）。
- スキルの最後に `pnpm content:validate` を実行する。

### 完了条件

- 1県分を①〜④で作り、`pnpm content:validate` を誤りなしで通るYAMLができる。

### テスト条件

- 確認の方法（LLMの出力なので、決まった入力・出力の自動テストにはしない）：
  - 検証エージェントに、わざと誤りを入れたYAMLを渡す（出典と違う数値、派生版で加えた事実、ふりがなの誤り、文字数の超過）。すべてが指摘されることを確かめ、結果をPRに書く。
  - 出典のURLが、実際に開いて確認できたものだけになっていることを確かめる（9.3）。

## T5-03 出典のリンク切れチェック

- **種別**：ci
- **依存関係**：T1-07
- **目的**：出典のリンク切れを、相手のサーバーに負担をかけずに見つけられるようにする。
- **参照仕様**：12.4、D15、R3

### 実装内容

- `scripts/check-links.ts`：
  - すべての `sources[].url` を集め、同じURLは1回だけ確かめる。
  - HTTPステータス、リダイレクト先、タイムアウトを記録する。
  - 同時に送るリクエスト数と、同じホストへの間隔に上限を設ける。
  - 結果を Markdown のレポートにする。対象の県を指定できる。
- `.github/workflows/link-check.yml`：`workflow_dispatch`（対象の県を入力で指定できる）。レポートを Artifact に保存する。
- リンク切れのときに Issue を自動で作るかを決める（推奨：作らない。四半期に1回の手動実行なので、レポートを見て人が作れば足りる）。

### 完了条件

- `link-check` を手動で実行し、レポートが Artifact に保存される。

### テスト条件

- 単体（fetch を置き換える）：
  - 200、301 → 200、404、タイムアウトを、それぞれ正しく分類する。
  - 同じURLは1回だけ確かめる。
  - 同時のリクエスト数が上限を超えない。同じホストへの間隔が設定より短くならない。
  - 指定した県のURLだけを確かめる。
  - レポートの Markdown の形。

## T5-04 1県目（試行）

- **種別**：feat
- **依存関係**：T5-02、T0-06、T3-04
- **目的**：1県で制作の流れ（9.2 の①〜⑧）を最後まで通し、ほかの46県に広げる前に問題を直す。
- **参照仕様**：第9章

### 実装内容

- 1県を選ぶ（推奨：京都府。名物・名所の出典が見つけやすく、読みの難しい固有名詞も多いので、ルールの足りないところが見つかりやすい）。
- 9.2 の①〜⑧を実行する。レビュアーはプレビューURLで確認する。
- かかった時間と、見つかった問題を記録する。
- 問題を、スキル・エージェント・執筆ルール・レビュー基準に反映する（同じPRか、続くPRで）。

### 完了条件

- その県のすべての項目が `reviewed` で `main` に入っている。
- 見つかった問題を反映した。

### テスト条件

- CI（`pnpm content:validate`、E2E）が通る。
- レビュアーがプレビューURLでカードの表示を確かめ、PRを承認した（9.4）。

## T5-05 残りの46県（県ごとに繰り返す）

- **種別**：feat
- **依存関係**：T5-04
- **目的**：全県のコンテンツを `reviewed` にする。
- **参照仕様**：第9章、R8

### 実装内容

- 1県＝1PR。PRのタイトルは `feat: add content for <prefecture>`。
- 地方ごとにまとめて進める。いくつかの県を並行して進めてよい。
- 進み具合は YAML の `status` で分かるので、開発計画では管理しない。

### 完了条件（県ごと）

- その県のすべての項目が `reviewed`。
- `pnpm content:validate` に誤りがない。警告（文字数、出典なし）がある項目は、理由をPRに書いた。

### テスト条件（県ごと）

- CI（`pnpm content:validate`、E2E）が通る。
- レビュアーの承認（9.4）。
