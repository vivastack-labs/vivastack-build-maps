# 実装計画を作る

`AGENTS.md`、`.codex/rules/index.md`、計画・コーディング・テスト・役割分担の該当ルール、仕様・タスク定義・アーキテクチャを読む。開発計画のタスク着手依頼は `next-task` の手順と整合させる。計画作成だけでは実装・コミット・push・PRを行わない。

## 入力と調査

1. 入力が `.prd.md` または実装フェーズ表のある文書なら、依存がすべて `complete` の次の `pending` フェーズを選ぶ。名前・説明・完了条件・依存・範囲を抜き出す。完了済みしかなければその旨を報告し、依存で止まっていれば未完了の依存を示す。他のファイルは参考資料、文章は機能説明として読む。入力がなければ対象を聞く。
2. 作るもの・価値・利用者・コード上の位置、ユーザーストーリー、複雑さ（Small / Medium / Large / XL）を整理する。中核の成果物・成功条件・解釈・主要な技術判断が不明なら、既存資料で解消できるか調べたうえで推奨案と理由を添えて質問する。
3. `rg` と実ファイルで、類似実装、命名、エラー処理、ログ、型・スキーマ、テスト、設定・環境変数、依存を調べる。入口、データフロー、状態変化、契約、設計境界も追う。カテゴリ・ファイルと行・規約・実コード抜粋の表にまとめる。存在しないAPI・DBやパターンは作り足さない。
4. 外部技術が関わる場合はインストール版の資料、Context7や公式一次資料で版固有の注意を調べ、知見・適用箇所・落とし穴・URLを残す。Next.jsのコードを計画する前に同梱ドキュメントを読む。内部の既存パターンだけで足りるなら外部調査不要の理由を記録する。
5. UI変更は操作箇所ごとの変更前後と利用フローを図や表で示す。内部変更は該当なしと書く。採用方針・代替案と不採用理由・対象範囲・対象外を決める。

## 計画の内容

`.codex/plans/<タスクID>-<slug>.plan.md`（タスクIDがなければ `<slug>.plan.md`）へ日本語で保存する。

- 概要、ユーザーストーリー、問題から解決への変化、複雑さ、元PRD・対象フェーズ・見込みファイル数
- UXの変更前後と操作表、実装前の必読ファイル・行・優先度・理由、外部資料と要点
- 実コードと出典付きの再利用パターン（命名・エラー・ログ・データ処理・テストの該当分）
- 作成・変更するファイルと理由、対象外
- 依存順の作業。各作業に `ACTION`、`IMPLEMENT`、`MIRROR`、`IMPORTS`、`GOTCHA`、`VALIDATE` を具体的に書く
- 要件IDを持つテストの入力・期待結果、空・最大・不正入力、並行操作、通信失敗、権限不足のうち該当する境界条件。Red → Green → Refactor の順序
- `pnpm typecheck`、`pnpm lint`、部分テストは `pnpm vitest run <path>`、全体は `pnpm test`、`pnpm build` と期待結果。必要なE2E・手動検証。CSPは開発サーバーだけで確認しない
- 完了条件、規約・エラー・ログ・テスト・設定値・文書更新・範囲の確認、リスクの可能性・影響・軽減策、判断記録

全体80%以上・ドメイン90%以上のカバレッジ、UI・ルーティングのmerge前の手動E2E、画面変更PRのafter画像を計画に反映する。不要な検証や存在しない基盤の検証は要求しない。

## PRDと完了報告

Codex側PRDを入力にした場合だけ、選択フェーズを `in-progress` にして計画へのリンクを追加する。Claude側資源は参照専用。Claude由来のPRDを使う場合は出典を付けたCodex側の作業用文書を `.codex/prds/` に作り、そのフェーズだけを更新する。元文書を移動・更新しない。

実在する参照・抜粋、全作業の実装と検証手順、import、注意点、静的解析・テスト・ビルド、UXと境界条件を点検する。初見の実装担当が判断根拠を追える程度に不足を埋める。
保存先、元PRD・フェーズ、複雑さ、ファイル数・作業数、主要パターン、調査内容、リスク、実装の見通し（1〜10と理由）を報告する。次は `prp-implement` に計画を渡すよう案内する。
