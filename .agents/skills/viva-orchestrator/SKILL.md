# Viva Orchestrator

共通規約は `AGENTS.md` と `.codex/rules/index.md`、作業に該当するルールを読む。
入力はスキル名に続くユーザーの依頼文として解釈する。Claude用の引数展開には依存しない。
Claude側の設定・資源は変更しない。回答と成果物は日本語にする。

元の `.claude/commands/viva-orchestrator.md` のCodex版。
実装→独立レビュー→検証→後処理を進める。元のorch-*定義や専用モデルは前提にしない。

## 対象と状態

- 計画パス指定：その1件。未指定：`.codex/plans/*.plan.md` を更新時刻が古い順に処理する。
  completedは除く。対象がなければ変更せず終了する。
- `retry`：このworktreeの `.codex/orchestration/` の最新記録から再開する。
- 開始前に計画・承認範囲・ブランチ・作業ツリーを確認する。未承認の計画は実装前に確認する。
  Tタスクは `$next-task` の承認・検証・進捗規約も守る。
- 一意なrun IDで `.codex/orchestration/<run-id>.json` を作り、計画の絶対パス・内容のハッシュ、
  HEAD・ブランチ・worktree、ステージ、試行回数、担当ID、報告パス、結果を保存する。
  更新は一時ファイルから置換する。同じ計画の多重実行は認めず、実行中記録があれば止める。
  ロックは排他的に作り、ホスト・PID・開始日時・run IDを記録する。
  正常・失敗終了時に自分のロックだけ解放する。
  retryでロックが残っていれば、同じホストのPIDと開始日時、担当の生存状態を確認する。
  所有者の終了を確認できたロックだけ、旧runの中断を記録したうえで解除して再取得する。
  別ホスト・不明な所有者・生存中なら削除せず、重複実行を避けるため確認を求める。
  推奨は所有者の終了確認後のretry（理由：二重編集・二重コミットを防げるため）。
- 報告は `.codex/reports/<run-id>-<stage>.md`。認証情報はログに含めない。

## 4段階

| 段階 | Codexでの担当・操作 | 成功の条件 |
| --- | --- | --- |
| 実装 | task-implementer に計画・担当ファイル・条件を渡す。手順は `$prp-implement` | 完了条件を満たした実装報告 |
| レビュー | code-reviewer に全差分・未追跡・計画を渡す。必要ならsecurity-reviewerも | CRITICAL・HIGHが0件 |
| テスト | general-purpose に計画の検証だけを依頼し、編集は許可しない | 必要な検査が成功 |
| 後処理 | メインが差分・結果を確かめ `$prp-commit` の手順で対象だけをコミット | hooks込みのコミット成功、または変更不要の根拠 |

役割名を指定できなければ `.codex/agents/*.toml` のdeveloper_instructionsを依頼に渡す。
モデル・権限は親から継承する。ブランチ操作・コミット・PRはメインが担当する。
実装役にはオーケストレーター管理下で報告後に戻るよう伝え、計画の完了化・アーカイブは
レビュー・検証成功後、後処理のコミット前にメインが行う。
整理した計画・PRD・参照リンクの差分も確認し、必要な文書検査を通して同じコミットへ含める。Claude側の計画は参考に読むだけで、移動・編集しない。
委譲不可ならメインで可能な検証を行うが、独立レビュー未実施とし、後処理前に止める。
テスト未定義・未実行は成功にしない。該当しない検査は理由つき対象外とする。

## 再試行と再開

- 初回実装失敗・後処理失敗では自動再試行せず、報告して止める。
- レビューまたはテスト失敗だけ、元の実装役へ追加指示で修正を返す。
  担当IDが再利用できなければ、新しい実装役に計画・差分・失敗報告を渡し文脈の欠落を記録する。
- 修正は最大3回。試行回数を修正依頼前に永続化し、retryでもリセットしない。
  毎回レビュー→テストをやり直す。上限に達したら停止し、手動での判断事項を報告する。
- 記録はcompletedに加えてsuccess/failureを持たせる。最後の完了行だけで成功とは判定しない。
  retryでは最後に成功した工程の次、または失敗工程から再開する。
  中断した実装やコミットはGit状態と報告を確認してから再開し、コミットを二重実行しない。
- 計画ハッシュ・HEAD・ブランチ・worktree・報告が記録と食い違えば根拠を確認し、
  古い成功結果を流用しない。手動変更がある状態で勝手に再実行しない。
- 複数計画は1件ずつ処理し、失敗したら後続計画に進まない。

最後に計画・ブランチ、各段階の成否と報告パス、修正回数、未確認・次の手順を説明する。
この依頼には検証後のコミットを含むが、push・PR・merge・デプロイは含めない。
