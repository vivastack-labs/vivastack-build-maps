# next-task：Codex でタスクをPRまで進める

`.claude/skills/next-task/SKILL.md` の手順を参考にした Codex 版。
1タスク＝1ブランチ＝1PR（開発計画1.2）。共通規約は `AGENTS.md`、
Codex の実装・レビューのルールは `.codex/rules/index.md` と該当ファイルを読む。
以下のパス・コマンドはリポジトリのルートを基準にする。

Claude 側は参照だけにし、新しい計画は `.codex/plans/` へ保存する。
状態判定には既存の2つのスクリプトを読み取り専用の資源として再利用する。
スクリプト自体を変更せず、Claude の設定・計画・状態へは書き込まない。
例外として、Claude Code から引き継いだタスク（`.handoff/HANDOFF.md` の持ち主が `codex`）の
計画だけは、`.claude/PRPs/plans/` の元の場所のまま更新する（1タスクの計画を2つにしないため。
`docs/claude-codex-collab-design.md` 6.2）。

## 1. main を最新にする

まず `git status --porcelain` を確認する。既存の変更があれば切り替えず、その変更を
扱う方法を確認する。推奨は現在のブランチでのコミット（理由：stash は忘れやすい）。
既に扱い方が指示されていれば、その指示を使う。

`git config --get-all remote.origin.fetch` に `^refs/heads/screenshots` がなければ、
`git config --add remote.origin.fetch '^refs/heads/screenshots'` で除外する。
`git update-ref -d refs/remotes/origin/screenshots` で既存の追跡参照だけを消す。
画像のブランチ本体は消さない。

`git switch main` の後に `git pull --ff-only` を行う。fast-forward できなければ
ローカルとリモートの違いを伝えて止まり、勝手に reset・force push しない。

## 2. ローカルブランチを整理する

```bash
bash .claude/skills/next-task/scripts/branches.sh
```

`git fetch --prune` とPR照合の結果（TSV）を使う。`delete` はマージ／クローズ済みで
PR後のコミットがないブランチなので `git branch -D <branch>` で整理できる。
`ask` はPRなし・オープン中・PR後のコミットありなど。まとめて確認し、承認されたものだけ消す。
リモートにもないコミットあり／オープン中は保留を推奨し、
`local_only = 0` で作業を終えたブランチは削除を推奨する。理由も添える。
削除・保留したものを最後の報告に残す。

## 3. タスクを選ぶ

```bash
python3 -I .claude/skills/next-task/scripts/task_status.py
```

計画の状態・タスク定義の依存関係・GitHubのPRを突き合わせる。通信に失敗した結果を
「PRなし」と扱わない。利用可能なGitHubツールでも状態を確認できるが、不明なら明記する。

- 指定IDは依存関係が完了しているか確認し、未完了なら残りを伝えて判断を求める。
- ID未指定で候補が1件なら進める。複数なら表の先頭を推奨し、理由とともに選択を求める。
  作業中のタスクは先に伝える。
- 手作業のタスクはオーナーの担当として報告し、PRを作らない。
- 依存関係の補足も読み、部分的な制約を計画に含める。
- T5-05は県ごとのPRが続くため、マージ済みPRがあっても表の状態を正とする。
  スクリプトの `state`・`ready`・`needs_plan_update` と、それを使う依存判定をこの例外で見直す。

## 4. ブランチと進捗を用意する

`<種別>/<タスクID>-<英語slug>` でブランチを作る。
`docs/development-plan.md` の着手タスクを `作業中` にし、既にmerge済みのタスクは
実際の状態を確認して `完了` に合わせる。T5-05の例外を守る。
最初のコミットは `docs: <ID> を作業中にする`（完了に直すIDがあれば含める）。

## 5. 実装計画を作り、承認を得る

タスク定義、参照仕様・要件ID・D・U、開発計画の未決事項、該当するアーキテクチャを読む。
Next.jsを触るならインストール版の同梱ドキュメントも読む。

`.codex/plans/<タスクID>-<slug>.plan.md` に次を書く。過去の Claude 側の計画は参考に
読めるが、新規作成も既存計画の更新も Codex 側へ保存する。ただし Claude Code から
引き継いだタスクは、`.claude/PRPs/plans/` の計画をその場所のまま更新し、写しを作らない。

- 先に書くテスト：ファイル・テスト名・要件IDと、タスクの各テスト条件との対応
- 作る／変えるファイルと順番
- 完了条件ごとの確認方法
- 判断が必要な点のすべてと、それぞれの推奨案・理由

実装前に要点と判断事項をすべて示し、承認を得る。計画の確認要件は元スキルの手順5に由来する。
確認を求める際は、この計画ファイルと本スキルの該当箇所を示し、なぜ承認が要るか説明する。
既に同じ範囲が承認されていれば取り直さない。修正を求められたら計画を直して確認する。
承認後は `docs: <タスクID> の実装計画を追加` でコミットして残す。

## 6. TDDで実装する

委譲できる環境では `.codex/agents/task-implementer.toml` の役割を使う。
計画パス・ID・ブランチ・担当ファイル・一時ディレクトリ・承認時の条件を渡す。
ブランチ操作、コミット、push、PR、E2E、スクリーンショットを任せるかは明示する。
通常はメインがこれらを担当し、実装役はテストと実装に集中する。
モデルは親から継承する。利用できなければメインで同じ手順を実施する。

1. 要件IDのあるテストを書き、`pnpm vitest run <path>` で意図した失敗を確認する（Red）。
2. 通る最小の実装を書く（Green）。
3. イミュータブル・小さい責務・境界での検証を保ちながら整える（Refactor）。

Node.jsは `.nvmrc` の版を使い、必要なら `source ~/.nvm/nvm.sh` と `nvm use` で準備する。
仕様との差・計画変更は開発計画1.3に従う。日常的な実装判断は進め、
オーナーの判断が必要な違いだけ、推奨案と理由を付けて確認する。
後のタスクに関係する発見はその定義とPRにも残す。

報告の `status` に応じて進める。

- `done`：メインが差分を読み、手順7へ。
- `blocked`：既存の承認で判断できるか確認し、必要ならオーナーへ確認して同じエージェントへ返す。
- `failed`：失敗箇所と直し方を伝える。2回返して解消しなければメインで調べる。

## 7. 検証・レビュー・スクリーンショット

`pnpm lint`・`pnpm typecheck`・`pnpm test`・`pnpm build` をメインで確認し、
タスク固有の完了条件を1つずつ確かめる。失敗を出力の切り詰めで隠さず、終了コードを見る。
既に同じ差分に対して実行した検証は、結果を確認できれば不要に繰り返さない。
カバレッジは全体80%以上・ドメイン90%以上。

E2Eの対象を変えたら適切なローカル E2E を実行する。
UI・ルーティングを変えたPRでは、merge前に手動 workflow の成功も必要（D30）。
PRごとの自動起動には変更しない。プレビューの変更は `pnpm test:e2e:preview` も使う。

`.codex/agents/code-reviewer.toml` の役割に、計画、比較範囲、未コミット／新規ファイル、
完了条件を渡す。入力・外部通信・依存・権限などを変えた場合は `security-reviewer` も使う。
独立したレビューは並列にできる。レビューが使えなければ定義に沿ってメインで確認し、
独立レビュー未実施であることを報告する。

CRITICAL・HIGHを直し、MEDIUMもできるだけ直す。修正は同じ `task-implementer` に返し、
重要な指摘は再レビューする。子の報告だけで成功とせず、メインが完了条件を確認する。
hooks・検査を回避しない。

画面変更があれば `tests/screenshots/pages.spec.ts` の `SCENES` に必要な状態を足し、
準備完了を待つ。コミット後に `pnpm screenshots > <一時ディレクトリ>/screenshots.md` を実行する。
これは画像を `screenshots` ブランチへpushするので、タスクのPR用の画像としてのみ使う。
afterだけを撮り、出力の「画面の変更」の表をPR本文に貼る。撮り直したら表も差し替える。
画面が変わらなければ撮らず、「画面の変更なし」とする。

## 8. 計画を実際に合わせ、PRを作る

計画のテスト名・ファイル・判断を実際の内容に合わせ、末尾に「承認後に変えたこと」
（項目・承認時・実際・理由）の表を残す。なければ「なし」。計画をコミットし、
Markdownの検査を通す。進捗・タスク定義・仕様との不一致も解消する。
CHANGELOGはマイルストーン最後のPRと公開時だけ追記する。

タスクへの着手依頼にはPR作成までを含む。`git push -u origin <branch>` の後に、
日本語の本文をファイルへ書き、`gh pr create --title '<type>: <English description> (<ID>)' --body-file <file>`
で作る。利用可能なGitHubプラグインが必要な操作に対応する場合はそちらを優先できる。
merge・本番デプロイはここで行わない。

PR本文には次を含め、計画のパスは Codex 側を指す。

- 概要：タスクID、定義、`.codex/plans/<ID>-<slug>.plan.md` と目的
- 変更内容
- 画面の変更：afterの表、または「画面の変更なし」
- 判断したこと：項目・判断・理由の表、なければ「なし」
- 分かったこと：後のタスクの材料と、追記したタスク定義、なければ「なし」
- テスト：実行済みコマンドと結果、カバレッジ、完了条件ごとの確認、未確認の範囲

## 9. 報告する

PR URL・タスクID・残った判断事項・整理したブランチ・残る手作業を伝える。
次に着手できるタスクも示す。merge後の次回の実行で状態を `完了` に合わせる。
