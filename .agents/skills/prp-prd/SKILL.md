# PRDを作る

`AGENTS.md`、`.codex/rules/index.md` と `development-workflow.md` を読み、関連仕様・要件IDを確認する。入力は製品・機能の説明。実装や外部への投稿は行わない。

## 対話と調査

1. 入力がなければ何を作りたいか聞く。入力があれば理解を短く言い換え、ユーザーの応答を待つ。
2. 対象者、観測できる困りごと、既存の代替策と不足、今取り組む理由、成功の測り方をまとめて聞き、回答を待つ。
3. 類似製品、競合の解決方法、共通パターンと失敗例、最近の変化を調査する。既存コードがあれば関連機能・規約・制約も調べる。URLとファイル・行を添えて発見と情報不足を示し、考えの修正を受け付ける。
4. 理想の到達点、主な利用者の状況ときっかけ、JTBD（状況・動機・成果）、対象外の利用者、時間・予算・技術・法的制約を聞き、回答を待つ。
5. 技術面では、再利用可能な基盤・類似実装・接続点・依存・設定・型と、既存機能の入口からのデータフロー・境界・複雑さを調べる。独立した調査は利用可能なら並列に行う。コードがなければ技術方式と既知の難点を一次資料で調べる。実在する構成の説明と提案を区別し、実現性（高・中・低）と理由、再利用先、主要リスクを報告して制約の補足を受け付ける。
6. 仮説検証に必要な最小MVP、必須の2〜3機能と後回しの機能、測定可能な仮説、明示的な対象外、方針を変え得る未解決事項を聞き、回答を待って生成する。

既に得た回答を繰り返し求めない。判断を求める際は推奨案と理由を付ける。未確認の情報や数値を創作せず「未定・要調査」または仮定と検証方法を書く。外部調査ができなければ未確認の範囲を示す。

## 成果物

`.codex/prds/<kebab-case-name>.prd.md` に日本語で保存する。必要なディレクトリだけ作り、既存文書を無断で上書きしない。次の内容を含める。

- 問題と放置するコスト、根拠（発言・データ・観察または未検証の仮定）、提案と代替案を採らない理由
- 「この機能がこの利用者の問題を解き、この測定結果で確かめる」という主要仮説
- 対象外と理由、成功指標・目標・測定方法、未解決事項
- 主な利用者の現在の行動・きっかけ・成功状態、JTBD、対象外の利用者
- MoSCoWの機能・優先度・理由、MVP、価値に至る最短の利用フロー
- 技術的実現性、構成と依存、技術リスク・可能性・緩和策
- 実装フェーズ表：番号、名前、提供内容、状態（`pending` / `in-progress` / `complete`）、並列可否、依存フェーズ、計画へのリンク。各フェーズの目標・範囲・成功条件と並列可能な理由
- 決定・採用案・代替案・理由の記録、市場と技術の調査概要と出典、生成日時、検証待ちの下書きであること

問題の具体性と根拠、具体的な利用者、測れる仮説、範囲、未解決事項、着手判断に足る理由を確認する。出力では保存先、問題・解決策・主要指標、問題と利用者調査と実現性と指標の検証状況、未解決事項、フェーズと並列可否、推奨する次の行動と理由を報告する。計画へ進む場合は `prp-plan` にこのPRDを渡すよう案内する。自動で実装は始めない。
